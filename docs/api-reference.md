# Bramble HTTP API

Every route the macOS and iPhone clients talk to. Generated by hand against the code at
`bd8c0be`; the authority for response shapes is
`src/lib/api/views/views.types.ts`, which is where every field is assigned
explicitly and where the comments explaining each omission live.

See also `docs/import-api.md` for the design rationale behind the import
endpoints — this file is the contract, that one is the reasoning.

## Basics

**Base URL** — `http://localhost:3000` in development.

**Auth** — every `/api/v1/*` route and `/api/me` requires one of:

```
Authorization: Bearer <clerk session jwt>
Authorization: Bearer <guest token>
```

Clerk session tokens last about 60 seconds. Ask for one per request rather than
holding it; `AuthTokenProvider` on the client is shaped for exactly that.

**Guest tokens** are issued by `POST /api/v1/guests` to someone playing on the
iPhone before signing up (see _Guests and onboarding_). Keep the token in the
Keychain and send it as is: it lasts as long as the guest (seven days, its
`expiresAt`) and there is nothing to refresh. The server checks it against the
guest on **every** request, so it stops working the moment the guest expires,
is deleted or signs up — any of which is a plain `401`. The exceptions to "one of
the two" are the guest routes that come before a token exists
(`POST /api/v1/guests`, `POST /api/v1/guests/challenge`) and
`POST /api/v1/guests/claim`, which takes both.

A guest may use the whole play loop, `/api/me`, `/api/v1/me/preferences`,
`/api/v1/world`, people and storylines — all scoped to their own story, as for
anyone. **Imports need an account:** a guest gets `403 SIGNUP_REQUIRED` from
every `/api/v1/imports` route.

**Caching** — every `/api/v1` response sets `Cache-Control: private, no-store`.

**Bodies are always objects, never bare arrays.** An array cannot grow a field.
`{ "events": [...] }` can later carry `truncated`; `[...]` can only be replaced,
and the client on the other end is a shipped app that cannot be rolled back.

### Dates

Every timestamp is ISO 8601 **with milliseconds**, because `toISOString()`
always emits them.

Swift's `.iso8601` decoding strategy **rejects fractional seconds**. Use:

```swift
let formatter = ISO8601DateFormatter()
formatter.formatOptions = [.withInternetDateTime, .withFractionalSeconds]
```

Getting this wrong surfaces as a decode failure that looks like a server bug.

### Client identification

The macOS app sends its build on every request (the iPhone app sends
`ios/…`, which is never refused):

```
X-Bramble-Client: macos/1.2 (57)
```

Bramble for Mac has ended (2026-11-25): the server refuses **every** macOS
build, answering **426 Upgrade Required**, which the Mac app answers by
installing its last build (it shows that the app has ended and calls nothing):

```json
{
  "error": {
    "code": "CLIENT_TOO_OLD",
    "message": "This version of Bramble is too old. Please update."
  }
}
```

Treat 426 as terminal and show the message — retrying cannot help, and it is the
one error whose remedy the reader performs themselves.

**Only a client that identifies itself can be refused.** A missing header, an
unparseable one, or a platform other than `macos` is served normally — the web
app sends no header, nor does curl, nor does any Mac build from before the header
existed. The gate is off by default, and `GET /api/health` is never subject to
it, so an uptime probe keeps working even when every client is locked out.

### Errors

One envelope, every failure:

```json
{ "error": { "code": "NOT_FOUND", "message": "Storyline not found: …" } }
```

`fields` appears on validation failures, keyed by the offending path:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "…", "fields": { "turnId": "Required" } } }
```

`retryAfter` (seconds) appears on `RATE_LIMITED`, `UPSTREAM_BUSY`,
`GENERATION_TIMEOUT` and `REPLY_PENDING`.

| Status | Code                        | Meaning                                                                                                                  |
| ------ | --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 400    | `VALIDATION_ERROR`          | Malformed body or a path id that is not a uuid                                                                           |
| 401    | `UNAUTHORIZED`              | Missing, malformed or rejected bearer token                                                                              |
| 403    | `FORBIDDEN`                 | Account deleted; device not verified (guest creation); onboarding as an account                                          |
| 403    | `SIGNUP_REQUIRED`           | A guest asked for an account-only thing: a fourth beat, an import, account deletion, stories from ChatGPT                |
| 403    | `REVERIFICATION_REQUIRED`   | Deleting an account needs a sign-in from the last 10 minutes. Re-verify, then resend                                     |
| 404    | `NOT_FOUND`                 | Unknown id — **or someone else's**. Never 403                                                                            |
| 409    | `CONFLICT`                  | A turn already answered with a _different_ choice; an attested key with a live guest                                     |
| 409    | `STORYLINE_NOT_READY`       | Storyline is not `ready` to play                                                                                         |
| 409    | `IMPORT_LIMIT_REACHED`      | All three conversation slots are spent                                                                                   |
| 409    | `GENERATION_IN_PROGRESS`    | Another generation holds this session                                                                                    |
| 409    | `REPLY_PENDING`             | Someone in the story replies later and it isn't time yet (see "Replies later"). Nothing written or spent. `Retry-After`  |
| 410    | `TRANSCRIPT_EXPIRED`        | Transcript gone before the worker read it. Re-send                                                                       |
| 413    | `TRANSCRIPT_TOO_LARGE`      | Over 400,000 characters                                                                                                  |
| 429    | `RATE_LIMITED`              | Out of energy — or, on the guest routes, too many from one address; or no stories from ChatGPT left today. `Retry-After` |
| 429    | `UPSTREAM_BUSY`             | The model provider throttled us. Clears on its own                                                                       |
| 500    | `GENERATION_UNUSABLE`       | Model output did not match the schema. Retrying burns money for the same failure                                         |
| 500    | `INTERNAL_SERVER_ERROR`     | Unexpected                                                                                                               |
| 502    | `APPLE_REVOCATION_FAILED`   | Account deletion: Apple refused the code. Nothing was deleted                                                            |
| 502    | `ANALYTICS_DELETION_FAILED` | Account deletion: PostHog refused. The account is not deleted                                                            |
| 503    | `GENERATION_FAILED`         | Provider failure. Retryable                                                                                              |
| 504    | `GENERATION_TIMEOUT`        | Our own 60s deadline. Safe to retry                                                                                      |

**404 and not 403 for another account's ids, everywhere.** "Not yours" and "no
such thing" are the same answer, or the error itself confirms the id exists.

## Infrastructure

### `GET /api/health`

No auth.

```json
{ "status": "ok" }
```

### `GET /api/me`

```json
{
  "id": "uuid",
  "email": "great@brambleworld.com",
  "shareUsage": true,
  "isGuest": false,
  "isAdmin": false,
  "chatgpt": { "connected": true, "writing": false }
}
```

A guest gets the same shape with `"email": null`, `"isGuest": true`,
`"isAdmin": false` and `chatgpt` both false.

**`isAdmin`** is whether this reader is on the Bramble team. Always present.
An admin has unlimited energy (see _Energy_) and the server sends no analytics
about them, so **a client should send none either**: treat `isAdmin: true` like
`shareUsage: false` for capture. It is only ever the reader's own — no response
says anything about another account's role. Set in the Clerk dashboard, never by
a client (see `docs/deployment.md`, _Making someone an admin_).

**`chatgpt`** is Bramble in ChatGPT (`/api/mcp`, below): `connected` once the
account has used it (it isn't cleared when someone disconnects in ChatGPT, which
doesn't tell us), and `writing` while a story asked for there is being written.

**`id` is the analytics identity.** The Mac identifies the person in PostHog as
this uuid, lowercased, and the server sends its own events under exactly the
same value — so one human is one PostHog person. If the two ever disagree, every
funnel silently splits in half. A guest's id is their identity from the first
screen; it stays the same when they sign up as a new account, and changes only
when their story merges into an existing one (see `POST /api/v1/guests/claim`).

**`shareUsage`** is the analytics opt-out, so the settings toggle has a value to
render without a second request. Change it with `PUT /api/v1/me/preferences`.

### `PUT /api/v1/me/preferences`

```json
{ "shareUsage": false }   →   200 { "shareUsage": false }
```

`PUT` rather than `PATCH`: the body is the whole of the resource, so sending it
twice gives the same answer.

**Honoured server-side, not just in the app.** Every server event checks this
(and `isAdmin`) before it is sent, so turning it off stops the events rather than hiding the
toggle. Defaults to `true` for a reader who has never chosen — the events are
counts, durations and enums about the app's own behaviour, never anything the
reader wrote.

A non-boolean is a **400** with `fields.shareUsage`. Works for a guest too.

### `PUT /api/v1/me/devices`

Registers this install for push notifications. Send it whenever iOS hands the app
a token, and after signing in.

```json
{ "token": "<hex from iOS>", "environment": "production", "timeZone": "America/New_York" }
→ 200 { "registered": true }
```

`environment` is `sandbox` for a Debug build and `production` for TestFlight and
the App Store. `timeZone` is an IANA name. Sending it again updates the row, and a
token already registered to someone else moves to this account.

A malformed field is a **400** with `fields`. A guest gets **403
`SIGNUP_REQUIRED`**: notifications are for accounts.

### `DELETE /api/v1/me/devices`

Stops notifications to this install. Send it **before** signing out, while the
session still authenticates. The token goes in the body, not the URL, so it stays
out of access logs.

```json
{ "token": "<hex from iOS>" }   →   200 { "removed": true }
```

`removed` is `false` if this account didn't have that token, which is not an error.

### `PUT /api/v1/me/notifications`

The notifications switch in settings.

```json
{ "enabled": false }   →   200 { "enabled": false }
```

Honoured by the server, which is what sends them. On until turned off.

A notification's payload carries `kind` (`battery_back`, `story_waiting`,
`story_ready` when a story asked for in ChatGPT has been written, or
`reply_arrived` when a reply someone in a story owed has been written; see
"Replies later"; or `duet_moved` when, in a story for two, the other player did
something this player's side will open with), so the app can tell which was
opened. A `duet_moved` tap should open the desk like any other; the next beat
of that story is the one that opens with the other player's texts. It never carries a name or a line of story.

### `DELETE /api/v1/me`

Deletes the reader's account, now and for good: every row they own (the
`users` row and everything that cascades from it), their Clerk user with its
passkeys and sessions, their PostHog person and its events, and — when the
account has Apple on it — their Sign in with Apple, revoked at Apple.
**204** with no body. The session token stops working.

Accounts only: a guest gets **403 `SIGNUP_REQUIRED`**.

**The player proves it's them first, and nothing is deleted until they have.**

- **An account with Apple** (a Clerk external account for Apple) sends a fresh
  Sign in with Apple authorization code. The app signs in with Apple again
  (`ASAuthorizationAppleIDProvider`, no scopes) and sends
  `authorizationCode`:

  ```json
  { "appleAuthorizationCode": "c1a2…" }
  ```

  The server trades it at Apple for a refresh token, checks it is the same
  Apple ID as the account's, and revokes it. Codes are single-use and live five
  minutes, so this is the re-verification too. Clerk can't re-verify with Apple,
  and Clerk holds no Apple token from a native sign-in, so there is no other way
  to revoke. Without a code: **403 `REVERIFICATION_REQUIRED`**. A code for a
  different Apple ID: the same 403. A code Apple refuses: **502
  `APPLE_REVOCATION_FAILED`**.

- **Any other account** sends no body. Its session must have re-verified a first
  factor in the last **10 minutes** — read from the session token's `fva` claim.
  On iOS: `Session.verifyWithPasskey()` or `sendEmailCode` /
  `verifyWithEmailCode`, then a fresh token (`skipCache`). Otherwise **403
  `REVERIFICATION_REQUIRED`**.

**Order, and what a failure leaves.** Apple is revoked, then the PostHog person
deleted, then the rows and the Clerk user go in one transaction — Clerk's delete
runs inside it, so if Clerk refuses, the rows roll back. A failure at any step
leaves the account in place and signed in, and the request can be retried with
fresh proof; the steps already done are harmless to repeat. A body with any
other field is a **400**.

## Guests and onboarding

The iPhone's first run: a new player plays **three beats** before being asked to
sign up. They are a real user from the first request — a _guest_ — so the play
loop below works for them unchanged. Signing up either turns the guest into the
account or moves their story into the account they already had.

```
POST /api/v1/guests/challenge   → challenge          (where attestation is required)
POST /api/v1/guests             → guest token
POST /api/v1/onboarding/answers → { flagged }        (reborn: up to three, before the opening)
GET  /api/v1/onboarding/opening → the first screen
POST /api/v1/onboarding/story   → beat 1             (scripted, no model call)
POST /api/v1/sessions/{id}/answer, POST .../turn     → beats 2 and 3
POST /api/v1/sessions/{id}/turn → 403 SIGNUP_REQUIRED
POST /api/v1/guests/claim       → { merged }        → POST .../turn → beat 4
```

**Limits for a guest, instead of energy:**

- **3 beats**, counted from the turns actually written across everything the
  guest owns: beat 1 (scripted) and two written by the model. With three turns
  written and none open, `POST .../turn` answers **403 `SIGNUP_REQUIRED`** —
  show the save sheet, never the sign-in screen, and keep the token. Resuming an
  open turn always works, and so does reading the story again
  (`GET /api/v1/sessions/{id}`).
- **No energy.** A guest never gets `RATE_LIMITED` from play, and `energy` is
  **`null`** wherever it appears (`GET /api/v1/world`, `GET /api/v1/sessions/{id}`,
  `POST .../turn`). Once they sign up, the turns they played count toward the
  account's energy like any other turns.
- **Seven days.** An unsaved guest, story and all, is deleted when it expires.

### `POST /api/v1/guests/challenge`

No auth. No body. **201**:

```json
{ "challenge": "x3f…", "expiresAt": "2026-10-29T08:05:00.000Z" }
```

A single-use challenge for App Attest, good for five minutes and one attempt.
Hash **the UTF-8 bytes of this exact string** with SHA-256 and pass that as
`clientDataHash` to `DCAppAttestService.attestKey`. Served whether or not the
server currently requires attestation, so the app has one flow everywhere.
Limited to 30 per address per hour (`429 RATE_LIMITED`).

### `POST /api/v1/guests`

No auth. **201**:

```json
{
  "token": "eyJ…",
  "expiresAt": "2026-11-05T08:00:00.000Z",
  "user": { "id": "uuid" }
}
```

Body, where attestation is required (staging and production):

```json
{
  "attestation": {
    "keyId": "base64 key id from generateKey",
    "attestationObject": "base64 attestation from attestKey",
    "challenge": "the string from POST /api/v1/guests/challenge"
  }
}
```

Where attestation is off (local development, CI) the body may be empty, and any
`attestation` sent is ignored.

- **`user.id`** is the guest's id and their analytics identity from now on.
- **`expiresAt`** is when the guest and their story are deleted unless saved —
  and when the token stops working.
- A missing attestation is **400** with `fields.attestation`. An attestation
  that does not verify, or a challenge that is unknown, expired or already used,
  is **403 `FORBIDDEN`** — every such case the same answer. A failed attempt
  spends its challenge: get a new one before retrying.
- **One live guest per attested key.** A key that already holds a live guest is
  **409 `CONFLICT`**: generate a new key (and challenge) to start again. A key
  whose guest has expired may be reused.
- **10 guests per address per hour**, attestation or not: **429
  `RATE_LIMITED`** with `Retry-After`.

The attestation is verified for the App ID
`K555FJZF47.com.brambleworld.BrambleMobile` against Apple's App Attestation root,
in the production App Attest environment unless the server is configured for
development. Only the key id is kept, on the guest; no device identifier is ever
sent or stored.

### `GET /api/v1/onboarding/opening`

Guest token only (an account gets **403 `FORBIDDEN`**).

```json
{
  "opening": {
    "id": "are_you_up",
    "clockTime": "1:47",
    "dateLabel": "Saturday, June 14",
    "text": "hey. are you up?",
    "timeLabel": "1:47 am"
  }
}
```

The phone the first screen shows, before anyone is named — so nothing about who
is texting. Openings can be tested against each other without a release; the
answer is stable per guest, and `id` is what `POST /api/v1/onboarding/story`
needs.

### `POST /api/v1/onboarding/story`

Guest token only.

```json
{ "openingId": "are_you_up", "relationship": "ex", "name": "Jordan", "pronouns": "she" }
```

- **`relationship`** — `ex` | `old_friend` | `crush` | `boss` | `sibling`.
- **`name`** — trimmed; 1–24 characters, counted as a person sees them (grapheme
  clusters); no control characters.
- **`pronouns`** — `he` | `she` | `they`, optional. Absent means the story says
  "they".

**201**, with beat 1 — scripted, so no model call. Which script depends on the
guest: for an `ex` or a `crush` the server picks one of five premises behind the
same "hey. are you up?" (the wedding below, moving away, just broke up, saw you
tonight, found the photo; `src/lib/onboarding/premises.ts`), deterministically
per guest. Each premise is written separately for an ex (you were together, it
ended) and a crush (never together, feelings unspoken, what they want left
open), so beat 1 can differ by relationship as well as premise: found the photo
is a group photo for a crush, not a night on a roof. Other relationships, which
only older builds offer, get the wedding. Clients must render whatever beat 1
arrives, not a bundled copy of it.

```json
{
  "story": {
    "sessionId": "uuid",
    "storylineId": "uuid",
    "storylineTitle": "the night before",
    "person": { "id": "uuid", "name": "Jordan", "isSelf": false },
    "turn": {
      "id": "uuid",
      "headline": "Jordan is getting married tomorrow. And she just texted you.",
      "narrative": "You stare at the screen until it dims, then tap it awake again. Three dots appear. Then they're gone.",
      "choices": [
        {
          "id": "uuid",
          "label": "Text back: \"i'm up.\"",
          "description": null,
          "reply": "i'm up."
        },
        { "id": "uuid", "label": "Call Jordan right now", "description": null, "reply": null },
        {
          "id": "uuid",
          "label": "Leave it on read and try to sleep",
          "description": null,
          "reply": null
        }
      ],
      "surfaces": [
        {
          "type": "imessage_notifications",
          "clockTime": "1:48",
          "dateLabel": "Saturday, June 14",
          "notifications": [
            {
              "sender": { "id": "uuid", "name": "Jordan", "isSelf": false },
              "text": "i know it's late. i'm getting married tomorrow and i need to say something before i do"
            },
            {
              "sender": { "id": "uuid", "name": "Jordan", "isSelf": false },
              "text": "hey. are you up?"
            }
          ]
        }
      ]
    }
  }
}
```

`turn` is the same `TurnView` the play loop returns; from here, play with
`POST /api/v1/sessions/{sessionId}/answer` and `.../turn` as usual.

**One story per guest.** Calling again returns the story that exists, **200**
with the same shape — safe to retry after a lost response. It is the story as
written: a different name in the retry does not rewrite it. On a repeat, `turn`
is whichever turn is open, or **`null`** once the guest has answered it and the
next one is not written yet (call `POST .../turn`).

An unknown `openingId` is **400** with `fields.openingId`; a bad `name`,
`relationship` or `pronouns` is **400** with that field.

The name and pronouns are stored with the story and sent to the model to write
the beats that follow. Nothing on this path logs them, and analytics never carries them.

### `POST /api/v1/onboarding/answers`

Guest token only (an account gets **403 `FORBIDDEN`**). The reborn onboarding's
three questions about the player's "last life", one answer per request, as the
player taps "next":

```json
{ "index": 2, "role": "ex", "text": "they left the week before graduation" }
```

- `index` — **1** (the choice you still wonder about), **2** (who changed the
  direction of your life) or **3** (what you were about to do).
- `role` — question 2 only, optional: `parent`, `ex`, `best_friend`, `teacher`,
  `boss` or `stranger`.
- `text` — trimmed, 1–140 characters counted as graphemes. Line breaks are
  allowed; other control characters are not.

The answer is checked for safety (OpenAI's moderation endpoint) before anything
is written. The check gets two tries (1.6 s, then 1 s if the first timed out or
OpenAI failed), so a response comes back within about 3 s; the iPhone waits that
long before moving on without it. **200**:

```json
{ "ok": true, "flagged": false }
```

- **`flagged: false`** — kept on the guest, replacing any earlier answer to the
  same question.
- **`flagged: true`** — it talks about self-harm, abuse or someone in danger.
  Nothing is kept, and any earlier answer to that question is deleted. Show the
  care check rather than moving on.

If the check can't be run, it's **429 `UPSTREAM_BUSY`** with `Retry-After`, and
nothing is kept: an answer is never stored unchecked. The iPhone waits about a
second for this response and moves on without it; a late `flagged: true` needs
nothing, since the answer was discarded anyway.

A skipped question sends nothing. A bad `index`, `role` or `text` is **400** with
that field. Safe to retry: the latest answer to a question wins.

The text is sent to OpenAI and stored. Nothing on this path logs it, and
analytics never carries it. Answers move with everything else when the guest
claims an account.

### `DELETE /api/v1/onboarding/answers/{index}`

Guest token only. "i'd rather not say" on a question already answered: deletes
that answer. **204** whether or not there was one, so it's safe to repeat. An
`index` other than 1–3 is **400**.

### `POST /api/v1/guests/claim`

Both identities at once:

```
Authorization: Bearer <clerk session jwt>
X-Bramble-Guest: <guest token>
```

Body optional: `{ "method": "apple" | "passkey" | "email" }` — how they signed
up, for analytics only.

```json
{ "merged": false, "user": { "id": "uuid" } }
```

- **`merged: false`** — the Clerk user had no Bramble account, so the guest
  _became_ it. `user.id` is the guest's id, unchanged.
- **`merged: true`** — they already had an account. The guest's story moved into
  it: its people, storyline and playthrough, with the guest's "you" merged into
  the account's, and its reborn answers, which replace the account's answers to
  the same questions. `user.id` is the **account's** id; the guest id no longer
  exists, so identify analytics with the new one.

Either way the guest token stops working immediately, and the `sessionId` the app
holds still names the same playthrough — call `POST .../turn` with the Clerk
token for beat 4, which costs energy like any turn.

If the Clerk account's email already belongs to a different Bramble account, the
claim is **409 `CONFLICT`**; if the Bramble account was deleted, **403
`FORBIDDEN`**. In both cases the guest is left as it was.

A missing or rejected Clerk session is **401**; so is a guest token that is
expired, unknown or **already claimed**. A retry after a lost response therefore
gets 401 even though the claim happened: on 401 here, check `GET /api/me` with the
Clerk token before treating the story as lost.

## The world — what there is to play

### `GET /api/v1/world`

The twenty most engaging moments across every storyline the reader owns, best
first. This is the discovery surface: **most of these are beats the reader has
not reached**, and that is deliberate — you cannot offer "play from here"
without saying where "here" is.

Query: `?limit=` — optional, clamped to 20.

```json
{
  "events": [
    {
      "eventId": "uuid",
      "storylineId": "uuid",
      "storylineTitle": "The Unsent Apology",
      "title": "The apology that landed wrong",
      "description": "An apology was offered and waved away before it finished.",
      "occurredAt": "2026-04-02T18:00:00.000Z",
      "people": [
        { "id": "uuid", "name": "Blossom", "isSelf": true },
        { "id": "uuid", "name": "Maya", "isSelf": false }
      ],
      "score": 9,
      "weight": 1,
      "playthrough": {
        "sessionId": "uuid",
        "turnsAnswered": 4,
        "lastActiveAt": "2026-05-01T09:30:00.000Z"
      }
    }
  ],
  "truncated": true,
  "current": {
    "sessionId": "uuid",
    "storylineId": "uuid",
    "storylineTitle": "the night before",
    "turnsAnswered": 4,
    "lastActiveAt": "2026-10-30T19:58:00.000Z",
    "waiting": null
  },
  "energy": { "remaining": 14, "limit": 20, "resetsAt": "…", "fullAt": "…" }
}
```

- **`score`** — 1–10, written by the model against an absolute rubric, so scores
  from different storylines are comparable.
- **`weight`** — 0..1, normalised across _this response_. Use it to size or
  colour; `score` is there so you can change that mapping without a server
  release.
- **`people`** — people, not per-storyline characters, so one human is one object
  however many storylines they appear in. Reader first, then alphabetical.
- **`occurredAt`** — null when the conversation did not date the beat.
- **`playthrough`** — the reader's most recent session opened at this beat, or
  `null`. What turns "play" into "continue" on the card. Always present, so
  branch on the value rather than on a missing key. Loaded for the whole page in
  one query.
- **`truncated`** — more rankable beats exist than were returned.
- **`current`** — the story the reader is in now: their most recently active
  session, whatever it was opened from, or `null` if they have never played.
  `{ "sessionId", "storylineId", "storylineTitle", "turnsAnswered", "lastActiveAt", "waiting" }`,
  `waiting` as on the session (see "Replies later").
  The iPhone's desk resumes it (`GET /api/v1/sessions/{id}`) to light the phone
  for its waiting beat. Always present; branch on the value.

A reader with nothing gets `{ "events": [], "truncated": false }` and **200,
never 404**. Empty is an invitation, not an error.

Beats with no score are excluded entirely rather than ranked last — null means
nobody asked the model, which is not the same as the model judging a beat dull.

## People and arcs

### `GET /api/v1/people/{personId}`

```json
{
  "person": {
    "id": "uuid",
    "name": "Maya",
    "isSelf": false,
    "relationshipType": "oldest friend",
    "arcs": [
      {
        "storylineId": "uuid",
        "title": "The Unsent Apology",
        "setting": "Two flats and a group chat, March to June.",
        "tone": "wistful",
        "role": "supporting",
        "lastPlayedAt": null,
        "startable": true
      }
    ]
  }
}
```

`arcs` is ordered most recently played first; never-played fall to the back.
`startable` is false while a storyline is still generating or has failed.

Until several conversations are imported, every person yields the same single
arc with the same title. That is sparse data, not a bug — collapse the arc list
into the person screen when there is one entry.

### `GET /api/v1/storylines/{storylineId}`

```json
{
  "storyline": {
    "id": "uuid",
    "title": "The Unsent Apology",
    "setting": "Two flats and a group chat, March to June.",
    "tone": "wistful",
    "startable": true,
    "cast": [{ "id": "uuid", "name": "Maya", "isSelf": false }]
  }
}
```

**`cast` contains only people the reader has met** — those appearing in a beat at
or below their playhead. Extraction writes character descriptions having read the
whole conversation, and one really did read _"the investor who offers $300,000"_,
so an uncut cast puts the ending on the first screen.

No `arcSummary` and no `description`: both describe the whole arc.

## The play loop

Two calls. `turn` brings a session to a playable state and returns what to show;
`answer` records a decision and is deliberately fast.

### `POST /api/v1/storylines/{storylineId}/sessions`

Body optional:

```json
{ "mode": "resume", "fromEventId": "uuid" }
```

`resume` (the default) returns the existing playthrough if there is one; `new`
forces a fresh one. **201**, with the same `SessionView` the resume probe
returns.

**`fromEventId`** is how the world screen's "play from here" works: pass an
`eventId` from `GET /api/v1/world` and the new session's playhead lands **on**
that beat, so the story continues from it.

- **`mode: "resume"` (the default) returns the reader's most recent playthrough
  opened at that same beat**, or creates one. One playthrough per moment: tap a
  moment, play, come back a week later, tap it again, and you land where you
  left off. Two rapid calls cannot produce two sessions.
- **`mode: "new"`** always creates another playthrough of that beat, so a
  deliberate replay stays possible.
- Resume is keyed on the beat, not the storyline. A session started from the top
  is never adopted by a moment, and two different moments are two playthroughs.
- A beat from a different storyline, or one that does not exist, is a **404** —
  the id is resolved against the storyline named in the path.
- A malformed id is a **400** with `fields.fromEventId`.
- Picking a beat _behind_ another playthrough is fine. This starts a new session,
  so the monotonic playhead guard — which stops a retried generation walking a
  reader backwards _within_ a playthrough — never comes into it.

### `GET /api/v1/sessions/{sessionId}`

The resume probe. Free, no model call — call it on every launch rather than
reconstructing state locally.

```json
{
  "session": {
    "id": "uuid",
    "storylineId": "uuid",
    "state": "awaiting_answer",
    "turnsAnswered": 3,
    "endedAt": null,
    "next": null,
    "nextStatus": null,
    "ending": null,
    "endingStatus": null,
    "turn": {
      "id": "uuid",
      "headline": "Maya just texted you at 1:47 AM.",
      "narrative": "You read it with the sound off, twice.",
      "isEnding": false,
      "choices": [
        {
          "id": "uuid",
          "label": "Text back: \"i still think about it\"",
          "description": "It may not land.",
          "reply": "i still think about it"
        },
        { "id": "uuid", "label": "Change the subject", "description": null, "reply": null }
      ],
      "surfaces": [
        {
          "type": "imessage_notifications",
          "clockTime": "1:47",
          "dateLabel": "Saturday, June 14",
          "notifications": [
            {
              "sender": { "id": "uuid", "name": "Maya", "isSelf": false },
              "text": "i have to tell you something"
            },
            { "sender": { "id": "uuid", "name": "Maya", "isSelf": false }, "text": "are you up" }
          ]
        }
      ]
    },
    "history": [
      {
        "turn": {
          "id": "uuid",
          "headline": null,
          "narrative": "The message sits there, unsent.",
          "isEnding": false,
          "choices": [
            { "id": "uuid", "label": "Say the true thing", "description": null, "reply": null }
          ],
          "surfaces": []
        },
        "chosenChoiceId": "uuid"
      }
    ]
  }
}
```

**`history`** is every turn already answered, **oldest first**, each with the
choice that closed it. The open turn is deliberately absent — it is returned as
`turn`, and carrying it in both would make the client render it twice. Always
present: `[]` for a session that has answered nothing.

A reader resuming a moment they opened a week ago needs this; without it the
narrative refers to decisions they cannot see.

Four states, one remedy each:

| `state`           | What to do                                                     |
| ----------------- | -------------------------------------------------------------- |
| `awaiting_answer` | Render `turn` immediately                                      |
| `awaiting_turn`   | Call `POST .../turn`. `turn` is null                           |
| `blocked`         | The storyline is not playable                                  |
| `ended`           | The story is over. `turn` is its ending; show it, then move on |

With `awaiting_turn`, check **`waiting`** first: when it isn't null, someone in
the story replies later and `POST .../turn` answers `409 REPLY_PENDING` until
then. See "Replies later".

**`ending`** is the notebook's ending page, once the story has ended:

```json
"ending": {
  "title": "the train home",
  "summary": "you never said it. jordan got married, and you watched the first dance on your phone, alone.",
  "keyChoices": [{ "label": "you texted back at 1:48 am", "position": 0 }],
  "facts": { "choices": 14, "storyNights": 3, "peopleMet": ["jordan", "mae", "theo"] }
}
```

- Written once, moments after the ending turn, from this playthrough alone.
  **`null` until then**: read the session again shortly. If writing it fails,
  reading the session tries again (at most once every two minutes, however
  often you read), and so does a server sweep every five minutes, up to five
  attempts in all. Nothing else is needed from the app.
- **`endingStatus`** says which it is, on an ended session (null while the story
  is going):

  | `endingStatus` | What to do                                                                |
  | -------------- | ------------------------------------------------------------------------- |
  | `ready`        | `ending` is there: show the page                                          |
  | `writing`      | Not yet: keep reading the session ("writing how it ended…")               |
  | `unavailable`  | Every attempt failed and none will be made: stop waiting, go on to `next` |

- **`keyChoices`** — up to three of the reader's own choices, in story order:
  re-worded "you …", or, when the writer named none the reader made, the
  labels as the reader tapped them (first letter lowercased).
  `position` is the choice's place in its beat (0-based), so it takes that
  beat's choice colour.
- **`facts`** — `choices` made, `storyNights` (null when the story's clock
  doesn't say: leave it out of the line), and the people met, by name.

**`endedAt`** is when the story ended, or null while it is going. An ended
session stays the reader's `current` story in `GET /world` until they start
another, so the desk can show the ending.

Clients built before endings decode `ended` as an unknown state and show
nothing, which is safe.

There is deliberately no state for "answered, consequences pending" — the remedy
is the same call, and every state named here is a branch the client carries
forever.

### `TurnView` and story surfaces

Every turn has three parts, whatever it is shown on:

| Field       | What it is                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------ |
| `headline`  | The hook: one sentence saying what just happened. **Null on turns from before headlines.** |
| `narrative` | What you do or feel now. On a turn with no headline, the whole beat.                       |
| `isEnding`  | True on the story's last beat. An ending has **no choices** and is never answered.         |
| `choices`   | 2–4 options, in display order. `[]` on an ending.                                          |

**A choice** is `{ id, label, description, reply }`:

| Field         | What it is                                                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `label`       | What the choice is, in a few words: `Text back: "tell me."`, `Call Jordan right now`.                                                                             |
| `description` | One clause on what it risks. Often null.                                                                                                                          |
| `reply`       | **The exact words the reader sends as a text by picking it**, lowercase and casual like the story's texts — or **null** when the choice is an action, not a text. |

`reply` is always present. Show a choice with a reply as a message ready to send
in the thread, and one without as an action button; never parse the words out of
`label`. It is non-null only when the choice is literally sending a text to someone
in the scene: a call, putting the phone down, waiting, or saying something in
person is null. **Choices written before replies existed are all null**, so an
old turn shows every option as an action.

**Stories end.** Each storyline has a soft length of about 20 beats. From four
beats before it the model may end the story when it lands; four beats after it,
it must. So a story is roughly 16–24 beats, and its ending is shaped by the
choices made. **The first story** (the one begun from the 1:47 am phone) is
shorter: **its ending is beat 5** (beat 1 being the scripted one), with the
beats before it building to it: the first beat after signing up and the call is
the ending. One written during the 5-or-10 test (2026-11-25 → 11-27) keeps its
length. A first story already past beat 10 when endings shipped ends
on its next beat. Stories already in progress when endings shipped were given at
least their longest playthrough + 8 beats, so none ends without building to it.
**The Mac app never gets an ending** (`X-Bramble-Client: macos/…`): it can't show
one, so stories played there stay open. The ending is an ordinary generated turn and costs one point of
energy like any other. There is deliberately no "beats left" figure: the length
is a budget, not a promise.

**`surfaces`** is what the beat is _shown on_ — texts on a lock screen today, an
email or a boarding pass later. Always present; `[]` for a text-only beat, which
is most of them. Each entry is discriminated by `type` and carries only that
type's fields; none of them repeats the headline or the narrative, and the
narrative never repeats the words on a surface.

**Skip any `type` you do not recognise** and render the rest of the turn. New
types are added without a version bump.

| `type`                   | Fields                                                                                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `imessage_notifications` | `clockTime` (`"1:47"` or null — show the real clock), `dateLabel` (`"Saturday, June 14"` or null), `notifications`: 1–3 `{ sender: PersonView, text }`, **newest first**, never empty |

Senders are always people the reader has already met in this playthrough, and
never the reader. A sender whose person has since been deleted is dropped, and a
surface left with no notifications is dropped with it.

#### Proposed surfaces (not served yet)

The iPhone's desk has close-ups for an email on the laptop and a boarding pass
by the passport, built against these shapes from debug data. **Neither is
generated or served yet.** When the backend adds them, it should match these
fields, or update the iPhone in the same change: a payload in another shape is
skipped like an unknown type, so the beat falls back to the notebook rather
than failing.

| `type`          | Fields                                                                                                                                                                                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email`         | `from` (who it's from, as an inbox shows it: `"study abroad office"`), `timeLabel` (`"1:31 am"` or null), `subject`, `body`                                                                                                                                             |
| `boarding_pass` | `fromCode`, `fromCity`, `toCode`, `toCity` (`"JFK"`, `"new york"` → `"LIS"`, `"lisbon"`), `dateLabel` (`"FRI 10/03"`), `boardsLabel` (`"9:40 PM"`), `gate`, `seat`, `flight` (`"BR 214"`), `whenLabel` (how far off it is in the story: `"six days from now"`, or null) |

Labels arrive formatted, as `clockTime` does on texts. An email's `from` is a
name in the story, not a person the reader has met, so it is not a `PersonView`.

### `POST /api/v1/sessions/{sessionId}/turn`

The only paid endpoint. Writes the next beat, then works out what the reader's
choices changed after the response (oldest first), so the reader waits for the
beat alone.

No body. Returns `{ "turn": TurnView }` — the same shape nested in `SessionView`
above. Narrative and choices arrive **together**, so you hold the decision screen
before the reader has finished reading the beat above it.

Safe to retry: a second call finds the work done and costs a SELECT. Client
policy this is designed for — **single-flight per session**, jittered backoff, at
most three attempts, then a button. Never two concurrent.

Server deadline is 60s; past that you get `504 GENERATION_TIMEOUT`, which is
safe to retry.

On an ended session this returns the ending again, free and with no model call.

#### Replies later

A beat can end with someone replying later, in real time: "let me think. i'll
text you in the morning." Only a beat asked for by **iOS build 40 or later**
(`X-Bramble-Client: ios/… (40)`, `MIN_IOS_BUILD_FOR_PAUSES`) may pause: an older
app, or a request without the header, never gets one, whatever the rollout.
Answering it sets the session's **`waiting`**:

```json
"waiting": { "until": "2026-11-26T14:12:00.000Z", "kind": "tomorrow" }
```

- `kind`: `soon` (within an hour or so), `tonight` (a few hours) or `tomorrow`
  (the next morning, near when the reader usually plays). Say roughly when;
  never a countdown. No name: who replies is whoever the reader just answered,
  in `history`.
- Until `until`, `POST .../turn` answers **`409 REPLY_PENDING`** with
  `Retry-After` (seconds to `until`) and writes and spends nothing. There's no
  skip.
- At `until` (never between 22:00 and 09:00 where the reader is, and only once
  they have battery) the server writes the reply as the next beat, spending a
  point, and sends a `reply_arrived` notification ("2 new texts in your
  story."). Opening the app then finds it as the open turn. A reader who asks
  for it once it's due, before the server has, gets it written there and then.
- `waiting` is `null` with a turn open, on an ended story, and once `until` has
  passed.

A pause comes only in a story that isn't the reader's first, after at least six
beats in a day, at most once a day, and not as the story closes. It's rolled
out to admins first (`PAUSES_ROLLOUT`).

#### Streamed (`Accept: text/event-stream`)

Ask for `text/event-stream` and the beat arrives as it's written: its headline
and first text in a few seconds rather than the whole beat in 10–20. Without the
header nothing changes (older builds and the Mac app keep the JSON above).

Server-sent events, each `event: <name>` and one `data: <json>` line:

| Event     | Data                                                       | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `draft`   | `BeatDraftView`: `{ kind, headline, surfaces, narrative }` | The beat so far, **finished pieces only**, growing with each event: the headline, then each text (a whole one, never half), then the narrative. `surfaces` has the same shape as on `TurnView`. Show it as it grows; play a text's arrival when a new one appears. `kind` is `imessage_notifications` or `none` once the model has written it (null before): show a plain beat (`none`) from its headline, a texts beat from its first text. No choices yet. |
| `restart` | `{}`                                                       | The beat sent so far is being written again (it broke a rule only the finished beat shows, or the provider failed mid-way). Clear the draft; new `draft`s follow.                                                                                                                                                                                                                                                                                            |
| `done`    | `{ turn: TurnView, energy }`                               | The finished beat, exactly the JSON response above. It replaces the draft and brings the choices.                                                                                                                                                                                                                                                                                                                                                            |
| `error`   | `{ status, error: { code, message, … } }`                  | What the JSON response's error would have been, with its HTTP status.                                                                                                                                                                                                                                                                                                                                                                                        |

A refusal decided before anything is written (`429 RATE_LIMITED`,
`403 SIGNUP_REQUIRED`, `404`, …) is an ordinary JSON error response with its
status, never a stream. A beat already written (resuming an open turn, an ended
session) streams `done` alone. If the stream breaks, call again, streamed or
not: the server finishes and saves the beat regardless, and the next call gets
it at once.

### `POST /api/v1/sessions/{sessionId}/answer`

```json
{ "turnId": "uuid", "choiceId": "uuid" }
```

Returns `{ "turn": TurnView }`. Fast — one guarded UPDATE, no model call — so
fire `POST .../turn` immediately after and animate over the top of it. That
overlap is the whole latency budget of the loop.

`turnId` is the concurrency token, not a convenience: without it a screen
restored from the background can answer a turn the reader never saw.

**Self-reconciling.** Re-sending the _same_ choice returns 200, not 409, so a
lost response cannot strand you on an operation that succeeded. A _different_
choice is a real 409.

An ending cannot be answered: answering it is `409 CONFLICT`.

### The next story

Once a session is `ended`, its `SessionView` carries **`next`**: the story the
reader goes on to, like the next episode. Null while the story is going, and
null when there is nothing new for this reader (rare: the pool always has the
team's seed stories, but a reader can play them all).

**`nextStatus`** tells the two nulls apart, on an ended session (null while the
story is going):

| `nextStatus` | What to do                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------- |
| `ready`      | `next` is there: show the card                                                                                    |
| `preparing`  | Nothing yet, but a story the reader asked ChatGPT for is being written and will be `next`: read the session later |
| `none`       | Nothing can be offered: the reader has played everything there is for them. Offer making one with ChatGPT         |

```json
"next": {
  "title": "night bus",
  "hook": "the last bus home, and a stranger who knows your name.",
  "openingLines": [
    "you missed your usual bus.",
    "the last one is nearly empty.",
    "a stranger sits down beside you."
  ],
  "fromPool": false,
  "fromChatGPT": false,
  "withPartner": null
}
```

- **`hook`** — one line for the card: the setting and the situation, never what
  happens in the opening.
- **`openingLines`** — exactly three lines from the story's opening, shown one at
  a time before play. Lowercase, at most 40 characters each; the last is the
  moment the story begins, and none gives away anything past it.
- **`fromPool`** — written from another player's past. Show "written from
  someone else's past." when true; seed stories are the team's and say nothing.
- **`fromChatGPT`** — written for this reader from what they shared in ChatGPT.
  Show "made with chatgpt." when true. Never true with `fromPool`.
- **`withPartner`** — this reader's side of a story for two (see "Stories for
  two" below): the other player's first name, as they gave it. Null for every
  other story. A story for two is offered before anything else, like one from
  ChatGPT.

Pool stories are already written, so `next` is ready as soon as the story ends
whenever the pool has one for the reader; `preparing` only ever means a story
from ChatGPT. While one the reader asked for is still being written, `next`
waits for it for up to 90 seconds **from when they asked** (`preparing`), then
falls back to the pool. That holds even when a pool story was already shown for
this session: it's held back while theirs is written and comes back if theirs
isn't ready in time, so **keep reading the session while a pool story's card is
showing**, or a story written meanwhile won't reach the card. Theirs still
replaces the pool story if it's written before that one is started. Starting
(`POST /api/v1/sessions/{sessionId}/next`) always starts the story whose card was last shown, so a tap on a
card never fails because the wait began.

Otherwise it's the same story every time you ask for this session, so the card
shown and the story started match. Pool stories are written by other players (from their
answers to the reborn questions, rewritten so they can't identify anyone) or by
the team. A reader is never offered their own story, one they've already played,
or two by the same author in a row.

The exception is a story the reader asked ChatGPT for: it comes first, ahead of
the pool, as soon as it's written, and replaces a pool story already offered
here if the next story hasn't started. Only that reader is ever offered it.

### `POST /api/v1/sessions/{sessionId}/next`

```json
{ "how": "countdown" }
```

Starts `next` and returns `201 { "session": SessionView }` for the new session,
which is in `awaiting_turn`. Starting it is free (no model call). Then call
`POST .../turn` on it as usual. **That first beat is free too**, so autoplay
never spends battery the reader didn't choose to spend — but it still waits for
battery: at 0 it's a 429 like any other turn (see _Energy_).

`how` is optional and only for analytics: `countdown` (the countdown ran out),
`begin_now` (the default: the reader tapped it), or `later` (begun afterwards
from the notebook).

**Safe to retry:** asking again for the same ended session returns the same new
session. `409 CONFLICT` if the story hasn't ended; `404 NOT_FOUND` if there is no
next story.

The new session becomes the reader's `current` story in `GET /world`.

### `POST /api/v1/sessions/{sessionId}/report`

"Report this story": the reader telling us a story shouldn't be in Bramble. Any
session the caller owns, guests included, at any point, ended or not.

```json
{ "reason": "harmful", "turnId": "…" }
```

- `reason` (required) is one of `harmful`, `sexual`, `hateful`, `self_harm`,
  `real_person` (it seems to be about a real person), `other`. There is **no
  free-text field**: a player who wants to say more emails support.
- `turnId` (optional) is the beat on screen. It must be a beat of this session,
  or the answer is `404`.

Returns `200 { "report": { "id": "…", "reason": "harmful" } }`. Free (no model
call, no energy). **Safe to repeat:** one report per reader per story, and
reporting again keeps the latest reason and beat.

A report doesn't change the story. The team is alerted and reviews it, then keeps
it or takes it out of the pool (for players who haven't started it; anyone
already in it keeps their copy). The app should say so: "thanks. we'll look at
it." Nothing about the report is returned later.

## Conversation import

Full rationale in `docs/import-api.md`. Three conversations per account, ever.

### `GET /api/v1/imports`

```json
{ "limit": 3, "used": 1, "imports": [ ImportView ] }
```

`used` counts only `ready`. Compute remaining as `limit - used - pending`, where
`pending` counts `queued` and `running` from the array.

### `POST /api/v1/imports`

```json
{
  "conversationKey": "conv_3fa29b0c1d7e4a55",
  "transcript": {
    "surface": "imessage",
    "messages": [
      {
        "isFromMe": false,
        "handle": "c_9b1e04a7d2f3c611",
        "sender": "Maya",
        "text": "…",
        "sentAt": "2026-03-02T19:04:00.000Z"
      }
    ]
  }
}
```

- **`handle`** must be `"me"` or `c_` + 16 hex. An allow-list, not a
  "looks like a phone number" check — anything else is a 400.
- **`handle` is the identity.** It must be _stable per person across imports_ —
  the same human in two conversations needs the same `c_…` — and _distinct per
  person within one_. It is what `persons.source_contact_ref` hashes, so it is
  what makes someone the same row across storylines.
- **`sender` is a label, not an identity.** Two conversations may both contain a
  "Person A" without those being the same human; the backend never keys on it.
  Names should still be unique within a transcript, since the model uses them to
  refer to people.
- At least 50 messages, at most 400,000 characters of text, oldest first.

**202** when newly accepted and queued. **200** when an import for this
`conversationKey` already exists and has not failed — same body, nothing
started. A `failed` import with the same key is re-queued.

Returns in milliseconds; extraction happens in a background job.

### `GET /api/v1/imports/{importId}`

Poll every ~5s while `queued` or `running`. One indexed row read, no Redis.

```json
{
  "import": {
    "id": "uuid",
    "conversationKey": "conv_…",
    "status": "running",
    "stage": "casting",
    "storylineId": null,
    "failure": null,
    "createdAt": "2026-10-01T19:04:00.000Z",
    "updatedAt": "2026-10-01T19:05:12.000Z"
  }
}
```

- **`status`** — `queued` | `running` | `ready` | `failed`.
- **`stage`** — `reading` | `writing` | `casting`, only while `running`.
  Extraction is one model call, so progress is stages and not a percentage.
- **`storylineId`** — set once `ready`.
- **`failure`** — `{ "code": "…", "retryable": true }` when failed. Re-send on
  retryable; stop and show the error otherwise.

**No response ever carries message content.** Surface text is not an
exception: a notification is generated fiction written for the story, in a met
character's voice — the same kind of thing the narrative says about them — and
never a message from the imported conversation. The `imports` row holds none
either — the transcript lives encrypted in Redis for at most 30 minutes and in
the memory of the worker reading it, and nowhere else.

## Stories for two

One player invites another; both get the same premise from opposite sides,
each as their own story, offered as their next one. What crosses between the
two sides comes later; for now the other player is a character on each side,
by the first name they gave. All three routes speak first names only, never an
account's email or id.

### `POST /api/v1/invites`

Accounts only (a guest gets 403 `SIGNUP_REQUIRED`). Body: `{ "firstName": "Maya" }`:
how the inviter wants to be known in the other player's story, 1–16 letters
(spaces, hyphens and apostrophes allowed). **201**:

```json
{
  "invite": {
    "code": "KXMPRT",
    "url": "https://www.brambleworld.com/invite/KXMPRT",
    "expiresAt": "2026-12-03T04:12:00.000Z"
  }
}
```

Codes are 6 letters from `ABCDEFGHJKMNPQRSTUVWXYZ` (no I, L or O). An invite
lasts 7 days. At most 5 open at once and 10 made in 24 hours: past either, 429
`RATE_LIMITED` with `Retry-After`.

### `GET /api/v1/invites/{code}`

Accounts and guests, so the app can say who's inviting before asking to sign
up. The code in any case, spaces ignored. **200**:

```json
{ "invite": { "inviterFirstName": "Maya", "expiresAt": "…", "state": "open" } }
```

`state` is `open`, `accepted` or `expired`. An unknown code is 404 `NOT_FOUND`.

### `POST /api/v1/invites/{code}/accept`

Accounts only (403 `SIGNUP_REQUIRED` for a guest). Body: `{ "firstName": "Sam" }`,
as above. **201** `{ "duet": { "id": "…" } }`: both sides are written at once,
and each becomes that player's next story (`next.withPartner` is the other's
first name). Once only: the same player accepting again gets the same duet;
anyone else gets 409 `INVITE_USED`. 409 `OWN_INVITE` for your own, 410
`INVITE_EXPIRED` after 7 days, 404 for an unknown code.

### The invite link, `https://www.brambleworld.com/invite/{code}`

What `url` points at. **With Bramble installed, iOS opens it in the app**
(`/.well-known/apple-app-site-association` lists `/invite/*`), which reads the
code from the path. Without it, the website's page shows:

- `open`: "{name} invited you to a story together.", the code in large letters
  with "copy code", "open bramble and tap "got an invite code?"", and "get
  bramble on the app store" when `IOS_APP_STORE_URL` is set;
- `accepted` or `expired`: a line saying so, without the code;
- an unknown code, or anything that can't be one: a 404 page.

The code in the URL is read as the routes read it (any case, spaces ignored),
and any other spelling redirects to the uppercase one. The page is `noindex`,
sends no analytics, and its link preview (title and image) never names the
inviter: a preview is seen by anyone the link reaches. iOS can't carry a link
through a fresh install, and nothing here tries to (no fingerprinting): the
code is what survives it.

## Bramble in ChatGPT

### `POST /api/mcp`

An MCP server (Streamable HTTP, stateless, JSON responses) for ChatGPT's Apps
SDK: a ChatGPT user connects their Bramble account and asks for a story about
their life, which becomes their next story on iPhone. Not for the apps.

**Sign-in is OAuth 2.1, with Clerk as the authorization server.** Without a
token, or with one Clerk doesn't accept, `401` with
`WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/api/mcp"`;
that document names Clerk's issuer. Only tokens Clerk issued to ChatGPT's OAuth
client (`CHATGPT_OAUTH_CLIENT_ID`) are accepted (`403` otherwise), and only
here: session and guest tokens are refused, and an OAuth token is refused by
every other route. Accounts only.

Tools (`tools/list`):

- **`write_my_story`** `{ about, people: [{ name, relationship, details }] (1–3), you? }`
  — moderated, then queued; `{ outcome: "queued" | "limited" | "flagged", storyId, left }`.
  Five a day, shared with `POST /api/v1/stories/from-chatgpt`; one that couldn't be written doesn't count. What was sent is
  deleted once the story is written or refused. ChatGPT is told to call it as
  soon as the user asks, without showing them first (the iPhone's "make a story
  with chatgpt" link sends that request).
  A queued reply carries `openUrl` (`https://www.brambleworld.com/open/desk`),
  and ChatGPT is told to end its reply with it as "open bramble".
- **`my_stories`** — `{ stories: [{ storyId, status: "writing" | "ready" | "playing" | "not_written", title, requestedAt, reason }] }`.
  `reason`, only for `not_written`: `too_thin | not_a_story | unclear | weak | unsafe | failed`,
  so ChatGPT can ask for what was missing. Every safety code is `unsafe`.
- **`delete_my_story`** `{ storyId }` — deletes the story, its copy in the
  reader's world and the people it added; `{ deleted }`.

`GET` and `DELETE` are `405`: there is no stream or session.

### `POST /api/v1/stories/from-chatgpt`

Stories from a link ChatGPT wrote, for players without the plugin: the app
opens ChatGPT with a prompt, ChatGPT replies with
`https://www.brambleworld.com/open/story#<url-encoded note>`, where the note
is up to five situations from the player's life, and tapping it opens the app,
which sends the note here. No editing step and no confirmation: the tap is the
player's ok. Clerk bearer, **accounts only** (a guest is `403 SIGNUP_REQUIRED`).

```json
{ "context": "my ex Jordan texted me happy birthday…\n\nmy sister Maya…" }
```

- `context` (required): the fragment, decoded. Trimmed; 1–6000 characters, or
  `400 VALIDATION_ERROR` (`fields.context`).

A model (`chatgpt.situations`) sorts the note into at most five situations and
drops, whatever the note says, anything about health (including sexual health),
mental-health crises or self-harm, money, legal trouble, identifying details,
work or school logistics, anything sexual, and anything too thin to play. Each
situation kept is then exactly a `write_my_story` request: moderated (a flagged
one is dropped), kept in `chatgpt_contexts` until its story is written, written
by the pool job, and the player's next story. Only the situations are stored,
never the note. Stories from one link share a batch, so `story_ready` is sent
once, when the first is written.

The day's allowance (five, over a sliding 24 hours, shared with
`write_my_story`) is checked before the model is paid for. A link with more
situations than are left writes as many as are left, in the order the model
ranked them.

| Status | Body                                                                              | When                                                                                        |
| ------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 202    | `{ "outcome": "queued", "stories": 3, "left": 2, "overLimit": 0 }`                | `stories` (1–5) queued; `left` today after them; `overLimit` situations skipped for the day |
| 200    | `{ "outcome": "not_written", "reason": "not_a_story" }`                           | Nothing in the note to make a story from (or nothing left once dropped). Nothing is kept    |
| 200    | `{ "outcome": "not_written", "reason": "unsafe" }`                                | Moderation flagged every situation. Nothing is kept                                         |
| 429    | `RATE_LIMITED`, `Retry-After` (seconds)                                           | None left today; the header says when one comes back. The model isn't called                |
| 400    | `VALIDATION_ERROR`                                                                | No `context`, blank, or over 6000 characters                                                |
| 401    | `UNAUTHORIZED`                                                                    | No valid token                                                                              |
| 403    | `SIGNUP_REQUIRED`                                                                 | A guest                                                                                     |
| 5xx    | `GENERATION_FAILED`, `GENERATION_TIMEOUT`, `UPSTREAM_BUSY`, `GENERATION_UNUSABLE` | Sorting the note failed; nothing was kept or counted. Retry as the table above says         |

The stories then show in `GET /api/me`'s `chatgpt.writing` and, once written,
as the next story with `fromChatGPT: true`. Not idempotent: sending the same
note twice makes its stories twice (and uses the allowance twice), so the app
sends a link once.

Each request logs one `chatgpt_link_request` line in the web service: its
`outcome`, `stories`, `durationMs` (the whole request), `situationsMs` (the
model sorting the note) and `queueMs` (moderation and queuing). Counts and
times only, never the note.

### Opening the app from a link

`https://www.brambleworld.com/open/…` is a universal link: with the iPhone app
installed it opens on the desk (`/open/story#…` sends its note to
`POST /api/v1/stories/from-chatgpt` first). Without the app, or when the link
was opened inside another app's browser (ChatGPT's, where universal links don't
open apps), a page offers **open in bramble**, the app's own scheme with the same
path and fragment (`bramble://open/story#…`, built in the browser), and the app
for a player without it. The fragment never reaches the website. Each render of
that page logs `open_page_viewed` with its `kind` (`story` or `desk`) and
nothing else.
`/.well-known/apple-app-site-association` claims `/open` and `/open/*` for
`K555FJZF47.com.brambleworld.BrambleMobile`, and nothing else.

## What is never returned

Not oversights. Each is a field a client might expect and must not get.

| Field                                                        | Why                                                                                                                                                                                                                            |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `stakes`                                                     | What is at risk in a beat — the lever the model writes with, and most of every beat the reader has not reached                                                                                                                 |
| `generationRationale`                                        | The model explaining its own trick                                                                                                                                                                                             |
| `arcSummary`                                                 | Describes the whole arc, including beats above the playhead. (The ended session's `ending.summary` _is_ returned: it is written after the final beat from that playthrough alone, so it describes only what the reader lived.) |
| `narrativeOrder`, `playheadOrder`                            | Internal ordering keys. Start sessions from `eventId`                                                                                                                                                                          |
| `voiceProfile` / `sampleTurns`                               | Model-authored imitation of a real person's messages, learned from the conversation. (A surface's notification `text` is returned: it is a line of the story, like the narrative, not a sample of how someone writes.)         |
| `want` / `avoids`                                            | The authoring levers behind each character                                                                                                                                                                                     |
| `clerkId`, `userId`, `sourceContactRef`, `appAttestKeyId`    | Identity and contact join keys                                                                                                                                                                                                 |
| `durationMinutes`, `coverImageUrl`, any progress denominator | No honest backing — a story's length is a soft budget the model may overrun, so "3 of 20" is both a lie and a spoiler                                                                                                          |

A unit test stringifies every view and asserts none of these appear, so adding a
field by spreading a database row fails the build rather than shipping.

## Energy

Playing a turn costs one point from a daily allowance. Imports have their own
separate limit — three per account, ever.

```json
"energy": {
  "remaining": 14,
  "limit": 20,
  "resetsAt": "2026-10-03T09:12:04.000Z",
  "fullAt": "2026-10-03T23:40:51.000Z"
}
```

It rides as a **top-level sibling key**, never inside a resource, because it is
account state rather than session state. **`null` for a guest**, who has three
beats instead of energy (see _Guests and onboarding_):

| Route                             | Where                                                                   |
| --------------------------------- | ----------------------------------------------------------------------- |
| `GET /api/v1/world`               | the home screen, where a reader decides whether to play                 |
| `GET /api/v1/sessions/{id}`       | the resume probe                                                        |
| `POST /api/v1/sessions/{id}/turn` | read _after_ the turn, so it already shows the point this request spent |

- **`remaining`** — turns the reader may start right now, 0..`limit`.
- **`resetsAt`** — when the next point returns, or `null` at a full balance.
- **`fullAt`** — when the balance is full again: the last point spent coming
  back. `null` at a full balance. The iPhone's battery shows it as "full again".

**A sliding window, not a daily reset.** Each point returns exactly 24 hours
after it was spent, so energy trickles back through the day rather than arriving
in a lump at midnight — and there is no timezone to get wrong.

**An admin is unlimited** (`GET /api/me`'s `isAdmin`): `energy` is always full —
`remaining` equal to `limit`, `resetsAt` and `fullAt` null — and play never
answers `RATE_LIMITED` for energy, so no "battery back" notification is sent
either. Removing the role brings the ordinary count back at once, including the
turns played in the last 24 hours. Every other limit (ChatGPT's stories a day,
a guest's beats) is the same for an admin.

### What costs a point

Only **generating a new turn**. Specifically:

- **Resuming is free.** `POST .../turn` on a session with an unanswered turn
  returns it with no model call and no charge, even at zero energy. Being out of
  energy never hides the decision already in front of the reader.
- **Consequences are free.** They are owed work from a turn already paid for, so
  one point buys "the next beat, and what my last choice changed". A reader
  whose consequence failed and retried is not charged twice.
- **A failed generation costs nothing.** The balance is counted from turns that
  were actually written, so there is nothing to refund.
- **The first beat of the next story is free.** The beat a reader gets after
  going on from an ending (`POST .../next`) doesn't count, so autoplay never
  spends battery they didn't choose to spend. It still needs battery to be
  written: at 0 it waits, like any turn. The ending itself costs a point.

### When it runs out

**429** with `Retry-After` in seconds and the same value in the body:

```json
{ "error": { "code": "RATE_LIMITED", "message": "Rate limit exceeded", "retryAfter": 3041 } }
```

Treat it as expected, not exceptional: show the balance, show when it returns,
and re-enable play then. The reader can still read their open turn and browse
everything else.
